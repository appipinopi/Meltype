# 辞書の保存と共同編集

| データ | 編集元・正規保存 | 読込/配布 |
|---|---|---|
| システム辞書 | GitHubの `dictionaries/*.txt` | build.rsがFST索引と値データへ変換し、実行ファイルへ埋め込む |
| 英語/日本語/一般英語/固有名詞の前方一致索引 | 同じtxtから生成 | 4個のビルド済みFSTを直接照会 |
| 利用者の登録語・候補順 | プロファイルの `userdict.sqlite3` | セッションごとの候補キャッシュへ読み込む |
| 学習・定型文 | `state.json` | 従来どおり。ユーザー辞書の正規コピーは含まない |
| 他版との交換 | txt / JSON / XML plist | 既存の取り込み・書き出し・互換バックアップを維持 |

共同編集の手順は [dictionaries/README.md](../dictionaries/README.md)。txtからFSTを作るため、レビュー対象は引き続き読みやすいテキストです。並び順・コメント・改行を含む全バイトをFSTから復元できることを17ファイルで検査します。FSTだけで全候補の評価を行う実装ではなく、意味や翻訳などは従来の解析済みキャッシュも使います。速度やRAMの改善を保存形式だけから断定しません。

## SQLiteへの移行

旧 `state.json` / `userdict.txt` は、最初の正常な保存時に候補順を保って取り込みます。読み取りだけではDBを作りません。DBの空辞書も正規状態として扱い、削除済みの語を古いtxtから再取り込みしません。既存のファイルは自動削除しません。

`dictionary_readings` と `dictionary_entries(reading, position, word)` を同じトランザクションで更新します。application_idとuser_versionを確認し、不明なDB/将来版/破損はエラーにして上書きしません。読み取りは同じSQLiteスナップショットで行います。アプリの書き込みは従来のプロファイルロックで直列化し、SQLite側でもBEGIN IMMEDIATEと5秒のbusy timeoutを使います。辞書が変化していない学習保存ではDB行を書き換えません。登録語の変更時は候補順を含む辞書を一括置換するため、大辞書の編集コストは別途測定・改善の余地があります。

バックアップへSQLiteファイルやjournalを直接コピーしません。最新DBから辞書を読み、旧版が扱えるstate.json/userdict.txtを生成します。復元は事前検査とSQLトランザクション、観測できるエラー時のファイルの巻き戻しを組み合わせます。JSONとSQLiteの複数ファイルをまたぐ電源断時の原子性は保証しません。保存前のバックアップを利用してください。

## 確認範囲

- 共通Coreの209テスト。FSTの全バイト往復、SQLiteの候補順・再起動・旧語再出現防止・破損/将来版保護・同時編集・バックアップ往復を含む。
- 候補677シナリオ＋追加256シナリオはC#由来の固定結果と照合する。
- 全68設定の有限な試験値域だけで `2,067,895,430,987,964,852,731,904` 構成。追加ツール `tools/parity/settings-candidates/exhaustive.py` はoffset/limitで再開できるが、全件の実行完了を意味しない。
- 全文字列・数値・入力履歴・実OS辞書の全応答は網羅していない。Windows実変換器は同梱読み20,181件から128件と境界26件を選ぶ有限コーパスを用意した。実行結果は検証記録を参照する。
- Windows候補ウィンドウの7試験と位置/文節表示など15試験、設定UIの60項目/列挙名10表の一致と6ページ描画を確認。独立したWinForms画面と統合したRustページの構成差があり、全画面の同等性は未達。Mac/Linuxの実画面・ファイル選択・キーボード操作はCIのビルド成功だけでは完了にしない。
